## 修复后端 GET /chat/sessions 500 Internal Server Error

- **问题**：`GET /chat/sessions` 返回 500，Pydantic 报 `model_type` 校验错误——期望 `ChatSessionResponseSchema`，实际收到 SQLAlchemy `ChatSession` ORM 实例。
- **根因**：Pydantic v2 默认不自动将 ORM 模型转为 schema，需要 `from_attributes=True`（即 v1 的 `orm_mode`）。`ChatSessionResponseSchema` 和 `ChatMessageResponseSchema` 都缺此配置。影响三个接口：会话列表、创建会话、消息列表。
- **修复**：`backend/schemas/chat.py` 中两个 ResponseSchema 各加 `model_config = ConfigDict(from_attributes=True)`。
- **验证**：用系统 Python（`E:\Python\python3.10.4`，即实际运行服务的解释器）构造 ORM 实例后 `model_validate` 成功输出正确字段。注意：`.venv` 仍缺 pydantic 等依赖，服务实际跑在系统 Python 上。

## 修复聊天流式接口返回 network error

- **现象**：前端发送消息后显示 "network error"，后端流式接口 `POST /chat/sessions/{id}/stream` 返回 200 但立刻关闭连接（`transfer closed with outstanding read data remaining`）。
- **根因（直接）**：`.env` 中 `DEEPSEEK_MODEL=deepseek-chat`，但该 API Key 仅支持 `deepseek-v4-pro` / `deepseek-v4-flash`，调用 DeepSeek 返回 400 Bad Request；`llm_service.py` 里 `response.raise_for_status()` 在生成器内抛异常，导致 `StreamingResponse` 未发送任何数据就关闭连接，浏览器表现为 network error。
- **根因（并发隐患）**：原 `stream_chat` 为普通 `def` 端点，内部却用 async 生成器捕获 `Depends(get_db)` 创建的 SQLAlchemy session，ORM session 被跨线程使用，存在线程安全隐患。
- **修复**：
  1. `.env` / `.env.example`：模型名改为 `deepseek-v4-flash`；`.env.example` 中 API Key 改为占位符 `sk-your-deepseek-key`。
  2. `backend/services/llm_service.py`：将 `stream_llm_reply` 改为同步生成器（`httpx.Client`），并增加 API 错误捕获——出错时 yield 可读错误信息，不再让连接静默关闭。
  3. `backend/services/chat_service.py`：`send_message_and_stream` 改为同步生成器。
  4. `backend/routers/chat.py`：`event_generator` 改为同步生成器，使整次流式请求在 FastAPI 线程池单线程内执行，避免 SQLAlchemy session 跨线程。
- **验证**：curl 调用流式接口返回完整的 SSE 帧：`data: {"delta": "1"}` ... `data: {"done": true, "content": "1+1=2"}`，连接正常关闭。
- **说明**：服务实际运行在系统 Python `E:\Python\python3.10.4` 上，重启后生效。
